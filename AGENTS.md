# AGENTS.md

## Project

This is Bell Space, an Expo/React Native student app for Burbank High School.
Indoor maps and navigation come first; see `PROJECT.md` for the product scope.

Prioritize:

* mobile-first design
* smooth performance
* cross-platform compatibility
* maintainable code
* simple architecture
* small, focused changes

The project is currently at the **first UI version** stage: the app shell, a
campus map with three floors in one shared frame, and room selection, tested
on a physical iPhone in Expo Go.

---

## Scope Discipline

The AI is an implementation agent, not the project owner.

Implement the requested task without expanding its scope.

Do not independently begin future project systems just because they are mentioned in project documentation.

Current development direction:

```text
App shell + campus map (current)
    ↓
In-person checks (doors, paths, stairs, elevators, ramp)
    ↓
Verified route network + manual start → directions
    ↓
iPhone live-location experiment (current; POSITIONING_EXPERIMENT.md)
    ↓
Tune from measured walk tests
```

Live position never snaps to a room, never infers a floor, and drives
step progress or rerouting only when its measured accuracy allows it. The
GPS-to-map alignment comes only from measured reference points.

Unfinished functions in the UI must be clearly labeled (for example a
"Coming soon" badge). Do not add controls that pretend to work, such as
"Start directions" or a location button, before they do. Keep development
commentary (sources, tracing notes, uncertainty) out of student-facing
screens; record it in `CAMPUS_MAP.md` and the SVG `data-note` attributes.

Only the current stage/task should be implemented.

If a requested change would significantly alter the architecture, dependencies, project phase, or scope, stop and explain the change before implementing it.

## Current Map Architecture

All floors share one campus frame (see `CAMPUS_MAP.md`). Sources of truth:

* Floor 1 (ground, Buildings 1–3): `2026-10-21_campus-floor1.svg`
* Floor 2 (Buildings 2 and 3): `2026-10-21_campus-floor2.svg`; Building 1 Floor 2:
  `2026-10-04_floor2-labeled.svg` (flat export), placed by `B1_FLOOR2_PLACEMENT`
* Floor 3 (Building 1): `2026-10-21_campus-floor3.svg`

The campus SVGs are generated by `tools/campus-trace/campus.py`; edit that,
not the SVG coordinates. Floors are registered in `src/map/floors.tsx`.
Routes come only from the route data in `src/navigation/data/`, kept separate
from the SVGs: `building1Walkable.ts` (walkable open space, obstacles and
open-area destinations, routed by `areaRouting.ts`) and `building1.ts` (door
network for enclosed rooms, merged in `campusNetwork.ts`). `directions.ts`
holds the rules for what may be offered to students. Every node/edge has a status
(`checked`, `proposed`, `unknown`); student directions use only `checked`
data and end at doors, never at room labels. `ROUTE_REVIEW.md` is generated
from the data by `tools/route-review/generate.cjs`.

Map labels are native text planned by `src/map/labelPlan.ts`; the vector map
redraws only when the camera settles (`InteractiveMap.tsx`). Keep per-frame
work to arithmetic on the UI thread.

Do not:

* redraw an existing floor map
* replace the SVGs with React Native shapes
* create unrelated replacement maps
* rasterize the SVGs
* create separate SVG files for different zoom levels
* add rooms, doors, paths or geometry that the source does not show

New or extended floor maps must be traced from a supplied source. Mark
anything uncertain with `data-status="uncertain"` and a `data-note`.

The current map system should support:

* pan
* pinch-to-zoom (two-finger rotation is disabled in the UI)
* sensible zoom limits
* smooth interaction
* dynamic SVG Level-of-Detail (LOD)

### SVG Level-of-Detail

The detailed SVG represents the highest-detail version of the map.

When zooming in:

* reveal more information
* reveal smaller details
* reveal labels/details specified by the current map specification

When zooming out:

* progressively hide less-important details
* simplify the map
* keep important structural information visible

Use the same underlying SVG rather than switching between separate maps.

When possible, use SVG groups/layers and opacity/visibility based on the current zoom level.

Do not invent map features or decide on visual details that have not been specified.

## Architecture

Keep these concerns reasonably separated:

```text
SVG Map
   ↓
Map Rendering
   ↓
Gesture / Zoom State
   ↓
LOD / Detail Visibility
```

Do not introduce unnecessary architecture.

Avoid adding:

* backend services beyond the Chat/Updates pilot (`PILOT_SETUP.md`); keep access rules in
  the database migration and test them in `tests/pilot-rules.test.mjs`
* databases
* state-management libraries
* APIs
* authentication
* unnecessary abstractions
* unnecessary dependencies

Prefer the simplest implementation that satisfies the current task.

## Dependencies

Before adding a dependency:

1. Check whether the project already has a suitable dependency.
2. Check the current Expo SDK compatibility.
3. Prefer Expo-recommended libraries.
4. Do not add a dependency merely for convenience if the existing stack can handle the task.

## Expo / React Native

Follow the Expo rules already documented above.

Expo and React Native APIs must be checked against the project's installed Expo SDK rather than relying on model memory.

Before using an Expo/React Native API:

1. Read the major Expo version from `package.json`.
2. Use the matching Expo documentation.
3. Check `https://docs.expo.dev/llms.txt` when documentation or API behavior is uncertain.

Use the package manager already used by the project.

If `bun.lock` exists, use Bun-compatible commands.

When installing Expo-compatible packages, use:

```bash
npx expo install <package>
```

or the equivalent project package-manager command when appropriate.

Do not manually edit generated native `ios/` or `android/` directories when Continuous Native Generation is being used.
